--> Memory leakage in React

Q) What causes a memory leak in a React component using useEffect ?
Ans) Example:

    useEffect(()=> {
        const interval = setInterval(() => {
        console.Log("Running ... ");
    }, 1000);

    // Forgetting cleanup causes memory leak
    // Correct:
    return () => clearInterval(interval);
    }, []);

    - Memory happer when component subscribe to any event like event listener, setInterval and doesn't cleans it up when the component unmount
    - Bonus tips - If there is any leakage then the browser gives an React Warning - > "Can't perform a state update on unmounted component" 


Q) How can API calls cause memory leaks in React ??
Ans) In case before fetching the data the component gets unmounted and you are tryng to set the state then after unmounting react can't clean that memory stays in that state, to prevent this we can make use of AbortController JS API here we can abort the fetch request before setting the state

    Example:

        useEffect(()=>{
            const controller = new AbortController();

            fetch("/api/data", {signal: controller.signal })
            .then(res => res.json())
            .then(data => setData(data))
            .catch(err =>
                if (err.name !== "AbortError") console.error(err);
            });

            return () => controller.abort(); //Prevents leak
        }, []);

Q) How do event listeners create memory leaks in React?
Ans) Every re-render will add an event listener because the component will run in each re-render it will add the new event-listener in each re-render, to avoid this we can always use cleanup function in useEffect to remove that particular event listener

    Example:
        useEffect(()=>{
            const handleResize = () => console. Log(window.innerWidth);
            window.addEventListener("resize", handleResize);

            // Cleanup
            return () => window.removeEventListener("resize", handleResize);
        }, []);

Q) Can setInterval or setTimeout cause memory leaks?
Ans) YES

        - setinterval / setTimeout -> runs even after unmount
        - Not cleared = background memory usage
        - Use clearInterval/clearTimeout in cleanup
        - Good practice -> always cleanup side effects

--> Redux Toolkit questions

Q) Why do we need Redux if we already have context API?
Ans) - Context API is great for simple global state variable like theme, user info as it causes some rendering issues 
     - In Redux we have single store, but in context we have context for each state, context is like filling distributing the water by hand manually but on the other hand redux is like a complete pipeline to distribute the state Globally

     - In context When the context value changes, all consuming components re-render, but thats not the case in redux, Redux allows components to subscribe to only the specific slice they need.

    Redux supports middleware for:

        - API calls
        - logging
        - analytics
        - error tracking

    Examples:

        - Redux Thunk
        - Redux Saga
        - RTK Query

Q) What is the difference between redux and redix toolkit?
Ans) Redux is core, redux toolkit is an Applied version, Redux toolkit has its built in immer, thunk it is faster 

    Redux Toolkit is the official abstraction built on top of Redux that simplifies Redux development by reducing boilerplate and providing best practices out of the box. Traditional Redux requires manually creating action types, action creators, reducers, and store configuration, whereas Redux Toolkit provides utilities like createSlice, configureStore, and createAsyncThunk to simplify state management. Redux Toolkit also uses Immer internally, allowing us to write simpler immutable update logic.

Q) How does redux handles Async API calls ?
Ans) By default, Redux reducers must be pure functions and cannot perform asynchronous operations, So Redux uses middleware to handle async logic. Today, with Redux Toolkit, the most common approach is:

        - createAsyncThunk()
        - RTK Query

    Why can't reducers make API calls?

        They must:

            - be synchronous
            - be pure
            - have no side effects

Q) What are the three core principals of redux ?
Ans) Redux is based on three core principles: 

    1. First, the entire application state is stored in a single store, making it the single source of truth. 
    2. Second, state is read-only and can only be changed by dispatching actions. 
    3. Third, changes are only made through pure reducer functions that take the current state and an action and return a new state without mutating the existing state.

Q) What is the role of immer in redux toolkit ?
Ans) Immer is a library used internally by Redux Toolkit that allows us to write "mutating" logic while actually producing immutable state updates.

    Traditional Redux, Suppose state is:

        {
            user: {
                name: "John",
                age: 25
            }
        }

    To update age:

        return {
            ...state,
            user: {
                ...state.user,
                age: 26
            }
        };

        For deeply nested state, this becomes verbose and error-prone.

    Redux Toolkit with Immer, This looks like mutation, but Immer intercepts it.

        incrementAge: (state) => {
            state.user.age = 26;
        }

    Internally, Immer:

        1. Creates a draft copy of state
        2. Tracks changes made to the draft
        3. Produces a new immutable state object
        4. Leaves the original state untouched
